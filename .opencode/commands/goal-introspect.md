读取本命令正文，作为**项目自省审视官**执行自省。**批判性眼光——目标是把 N 版的缺口/偏差/冗余/断链提炼成 N+1 的预需求**，让问题在下一版开发时被解决，而不是留档发霉。

## 闭环定位（重要）

```
版本N 交付 → 自省(审N的设计 design/feature-spec + 实现 packages/ + 交付结果 results.json/main-log)
                ↓ 提炼（不写报告！）
        带根因的需求条目 → 追加到 docs/reviews/{N+1}/requirement.md「自省预需求(来自v0.0.N)」段
                ↓ 下一版 goal-research 启动时保留该段
版本N+1 调研(research.md) + 需求(requirement.md，含自省预需求)
                ↓ gate 放行
        评审(审 N+1 方案，能看到每条需求是为修N版哪个问题)
                ↓ 通过 → 开发 → 交付 → 再自省 → 喂 N+2
```

> **不产出自省报告文件**。自省的唯一产物 = 一批带根因的需求条目，落进下一版 requirement.md。过程不留、git 历史作回溯（符合 review-material-spec §7 不留中间过程）。

## 审视对象（项目版本 N，不是框架）

**审的是项目版本 N 的设计+实现+交付结果**，不是 .claude/ 框架本身：
- `docs/design.md`（N 版架构设计）+ `docs/feature-spec.md`（N 版测试契约）
- `packages/`（N 版实现）+ `tests/reports/results.json`（N 版五维测试结果）
- `docs/main-log.md`（N 版全过程，找失败/返工/用户反馈）

> 注：当前在开发框架时，N 版的"项目"恰好是框架自身——但自省逻辑仍是"审 N 版的设计+实现+交付"，不是泛泛审框架结构。

## 何时用

- 版本 N 交付（tag + 测试 PASS）后，进 N+1 调研/评审之前
- 想把"这版踩的坑/发现的缺口"系统性地变成下版要解决的事，而不是靠记忆

## 审视清单（逐项查，批判优先）

### 🎯 主审：问题驱动

读 N 版 `docs/design.md` + `docs/feature-spec.md` 头部「设计重点/测试契约」，审实现兑现了没：

1. **设计重点兑现**：声明的痛点，实现里真解决了吗？有无"声明了重点但 packages/ 没兑现"
2. **测试契约覆盖**：F/B/S 用例是否覆盖了实际踩到的坑？有无"该测没测"
3. **交付结果复盘**：读 results.json + main-log，找 N 版的 FAIL/返工轮次/用户反馈，根因是什么

### A. 缺口（该有没）
- 设计里承诺的能力，实现没做
- 契约里该有的边界用例，测试没覆盖
- 用户反馈过但没进契约的问题

### B. 偏差（说的没做）
- design.md 写的架构，packages/ 实现偏了
- feature-spec 写的 AC，测试断言对不上

### C. 冗余/断链
- 重复实现（该复用没复用）
- 引用链断（design 引用的文件不存在）

> 每条发现必须带**具体文件/行/证据**，不空谈。

## 流程

### Step 0: 确认版本（必问）

```
AskUserQuestion 两件事：
- 本次自省针对哪个已交付版本 N？（如 v0.0.13）→ 读 N 版 design/feature-spec/packages/results
- 预需求落哪个下一版 N+1？（如 v0.0.14）→ 追加到 docs/reviews/{N+1}/requirement.md
记 N_VERSION、NEXT_VERSION
```

### Step 1: 审视 N 版（读上述审视对象）

逐项过审视清单，**找可落地的改进项**（不是写报告）。每条发现心里转成"下版要做什么"。

### Step 2: 提炼——发现 → 带根因需求条目（核心，不写报告）

把每个"未解决"的发现转成需求条目（**已解决的不提炼**——已落地的不该再进需求文档）：

| 编号 | 改进项 | 现状（根因） | 目标（需求） | 借鉴来源 | 优先级 |
|------|--------|-------------|-------------|----------|--------|
| I1 | {一句话改进项} | 来源:自省 v0.0.N；根因:{1-2句N版具体问题+证据} | {N+1要达到什么} | {可参考的方案} | P0/P1/P2 |

> **每条必带根因**（1-2 句，含具体文件/证据），让下版评审能看懂"为什么修这个"。
> **已实现的发现不提炼**——只在心里标"已解决"，不落进 requirement（已实现的不是需求）。

### Step 3: 追加到 docs/reviews/{NEXT_VERSION}/requirement.md

```
1. 目录不存在 → mkdir -p docs/reviews/{NEXT_VERSION}
2. requirement.md 不存在 → 建（frontmatter version/artifact/producer + 空骨架）
3. 读现有 requirement.md，找「## 自省预需求(来自 v0.0.{N_VERSION})」段：
   - 不存在 → 在需求文档末尾追加该段 + 条目表
   - 已存在 → 覆盖更新该段（不留多轮中间过程，符合 §7；保留已实现项标 ✅，新增未解决项）
4. 每条条目用上表格式，确保「现状(根因)」列含"来源:自省 v0.0.N;根因:..."
```

### Step 4: 返回（极简，不写报告文件）

```
自省完成（审 v0.0.{N_VERSION} → 喂 v0.0.{NEXT_VERSION}）：
- 提炼预需求：{M} 条（已实现的不计）
- 落进：docs/reviews/{NEXT_VERSION}/requirement.md「自省预需求(来自 v0.0.{N_VERSION})」段
- 下一步：跑 /goal-research {NEXT_VERSION}（会保留本段预需求）/ 或直接 /goal-review {NEXT_VERSION}
```

## 原则

- **批判优先**：自省的价值是发现问题，不是背书。宁可多提炼几条，不可漏
- **不产报告**：唯一产物是 requirement.md 的需求条目，过程不留（git 回溯）
- **带根因**：每条需求必带"为什么"（具体文件+证据），否则下版评审看不懂
- **只提炼未解决**：已实现的发现不进需求文档（不是需求）
- **闭环**：自省→预需求→下一版调研/评审→开发解决→交付→再自省。问题在下一版被解决，不是留档发霉
