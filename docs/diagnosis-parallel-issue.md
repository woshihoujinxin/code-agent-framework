# 并发度问题诊断报告

## 问题现象
- 调研阶段可以多 agent 并行
- 开发阶段变成串行，执行缓慢
- 经常断开，无法自动继续

## 根本原因（已确认）

### 原因1：依赖链过长
**问题**：Planner 倾向于创建长依赖链（A→B→C→D）而非星型结构（→ TASK01）

**证据**：
- `code-planner.md` L93：`禁止过度线性依赖：尽量只依赖 TASK01` —— **软约束**
- 没有强制检查点来验证是否真的遵守了"依赖最小化"
- 没有并行度评估

**影响**：
- 5 个任务如果变成 A→B→C→D→E 长链，只能串行执行
- 即使有 10 个任务，如果都是长链，也无法并行

### 原因2：就绪集计算潜在bug
**问题**：orchestrator 的 DAG 解析可能在某些情况下出错

**证据**：
- `dev-quality-orchestrator.md` L338-339：就绪集计算逻辑看起来正确
- 但缺少边界情况处理：
  - 依赖列格式错误（如 `TASK01 TASK02` 而非 `TASK01,TASK02`）
  - 状态格式错误
  - 升级任务 ID（如 `TASK01-01`）的特殊处理

## 修复方案

### 修复1：强化 Planner 的依赖最小化约束

**修改 `agents/code-planner.md` L89-94**：

```markdown
**B2 任务拆分硬约束（违反即废）**：
- **先判项目类型**：纯前端（无后端/API/DB）→ 全部 FE；纯后端（无 UI）→ 全部 BE；全栈 → 按模块归属
- **任务总数 ≤ 5**（按功能模块合并）；**每任务 ≥ 3 个相关文件**（模块 = 入口 + 核心逻辑 + 配套测试/配置）
- **TASK01 必为基础设施**（配置 + 入口 + 依赖声明 + 骨架）
- **【硬约束】依赖最小化**：
  - 首选：无依赖（仅 TASK01 可无依赖）
  - 次选：只依赖 TASK01
  - 禁止：A→B→C 长链（超过 2 层依赖）
  - **必须通过并行度检查**：拆分完成后，计算"最大可能并行任务数"（无依赖任务 + 只依赖 TASK01 的任务数），若 < 2 则重新拆分
- DAG 图用 Mermaid `graph TD`，按依赖列生成箭头，无依赖任务作起始节点
```

### 修复2：添加并行度评估检查点

**在 Planner 完成后添加验证步骤**：

```markdown
## 产出前验证（强制）

在输出给主Agent前，必须执行并行度评估：

1. 统计各任务的依赖层数（层数 = 最长依赖链长度）
2. 计算最大可能并行任务数 = 依赖层数 ≤ 1 的任务数
3. **验证标准**：
   - ✅ 最大并行任务数 ≥ 任务总数的 40%
   - ❌ 否则必须重新拆分，减少依赖链

示例（5个任务）：
- 星型结构（→ TASK01）：最大并行 = 4/5 = 80% ✅
- 长链（A→B→C→D→E）：最大并行 = 1/5 = 20% ❌
```

### 修复3：强化 orchestrator 的 DAG 解析鲁棒性

**修改 `orchestrators/dev-quality-orchestrator.md` L334-346**：

```markdown
1. Grep dev-plan.md 任务行并解析 {ID | 状态 | 依赖}：
   Grep(pattern: '^\| [0-9]+ \| TASK', path: '{REPO_DIR}/docs/dev-plan.md', output_mode: 'content', '-n': true)
   表格列序固定：| # | 任务ID | 标题 | 状态 | 依赖 | 拆分理由 |

   **【解析容错】**：
   - 如果依赖列包含空格而非逗号（`TASK01 TASK02`），自动替换为逗号
   - 如果依赖列为空或 `无`/`none`/`None`，视为无依赖
   - 升级任务 ID（`TASK01-01`）按主任务 ID 处理（`TASK01-01` 依赖 `TASK01` 时视为 `TASK01`）

2. ✅集 = 状态 ✅ 的所有 ID
3. 就绪集（开发优先，**只取 ready_dev**——测试延后到 Phase 3，本阶段不处理 🔳）：
   - ready_dev = 状态 ⏳ 且「依赖列每项都在 ✅集」的任务（无依赖任务首批即就绪）→ 进开发批次
   - **【调试日志】**：每批计算后，向用户报告"本批就绪任务：{TASK_IDs}（共 {N} 个）"
4. ready_dev 为空时：
   - 仍有 ⏳ → 上游依赖未完成，等待不启新批
   - 有 🔄 → 该任务开发中断，**resume/重派 Dev 重做**（不等待，见「压缩后恢复机制」）
   - 无 ⏳ 且有 🔳 → **整版本开发完成，进入 Phase 3 测试阶段**（统一提测所有 🔳）
   - 全部 ✅/⚠️ → 直接进 Phase 4 收尾
5. 开发批次 = **全部 ready_dev（最大化并发，主动开足 agent，不等用户提醒拆分）**；仅当用户显式设 BATCH_SIZE 或 eff_BATCH 因 429 降档时，才取 min(eff_BATCH, |ready_dev|) 个。**异构优先**（全栈项目同批尽量混 FE+BE：若就绪集同时含 BE 与 FE 任务，优先各取一个，而非同类型扎堆），避免两个 BE 同时连 DB/写 API 的资源争抢。BATCH_SIZE=批次大小（见「并发度控制」）。
```

### 修复4：添加可视化调试输出

**向用户展示依赖结构和并行机会**：

```markdown
### 依赖结构分析（Planner 产出时自动生成）

**依赖层级**：
- 第0层（无依赖）：TASK01
- 第1层（依赖第0层）：TASK02, TASK03
- 第2层（依赖第1层）：无

**并行机会**：
- 首批并行：TASK02, TASK03（2个）
- 最大并行任务数：3/5 = 60%
```
