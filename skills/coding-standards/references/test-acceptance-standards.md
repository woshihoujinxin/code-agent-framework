# 五维测试验收标准（Dev / Planner / Tester 三方共享契约）

> **这是"什么样的代码才算通过"的唯一权威定义**。所有写代码的人（Dev）与验收的人（Tester）都按本文件的标准对齐，避免"开发时不知道标准、测试时才见标准"的返工。
>
> **谁必读**：**Dev（开发前必读）**、**Planner（写 feature-spec 契约时必读）**、**Tester（执行时按此验证）**。feature-spec 的 F/B/S/E/Q 用例是"本任务测什么"；本文件是"每个维度按什么标准查、什么算 FAIL"——两者合起来 = 完整测试契约。
>
> **其他角色同理**：任何"产出方"都要在动手前对齐"验收方"的标准（PM 对齐需求可测性、Planner 对齐 Tester 验收维度、Dev 对齐五维标准、Ops 对齐 E2E 环境需要）——**标准前置，验收才不返工**。

---

## 五维边界矩阵（各维管什么、不查什么——边界争议以本表为准）

| 维度 | 管什么 | 不查什么（归邻维） |
|------|--------|-------------------|
| correctness（功能） | 业务正确性：F 用例输入→预期输出 | 不查攻击面（→security）、不查边界/异常崩溃（→robustness）、不查代码风格（→quality） |
| quality（质量） | 代码可读性/命名/函数设计/重复/注释/一致性（前端含视觉 Anti-Slop 与令牌对齐） | 不查行为正确性（→correctness）、不查安全漏洞（→security） |
| robustness（健壮） | B 用例：边界值/空值/异常路径/资源释放/非法输入降级 | 不查恶意攻击（→security）、不查业务正确性（→correctness） |
| security（安全） | S 用例：注入/认证绕过/越权/密钥泄露/配置/依赖漏洞 | 不查崩溃与边界（→robustness）、不查业务功能（→correctness） |
| e2e（端到端） | E 场景：跨层全链路用户流程（含依赖服务启动） | 不重复单维验证（单维已覆盖的用例不重测） |

> **重叠判定**：同一问题既可归 A 又可归 B 时，Tester 按"问题本质"归类并在报告注明；边界争议以本表为准，超出本表仍存疑 → 回查 `role-contracts.md` 或由 Planner 裁决。

---

## 一、功能正确性（F）— correctness 验收基准

| 检查项 | 标准 |
|--------|------|
| 契约 F 用例逐条实现 | 每条 F 用例（输入→预期输出）都被真实实现，输入 X 确实产出 Y |
| 单测覆盖 | Dev 单测覆盖归属自己的每条 F 用例（一条用例一个单测函数），断言到位（不只验状态码，要验 body） |
| 契约外补漏 | 对照 PRD 用户故事，契约漏列的场景 Tester 会补充验证 |

**FAIL**：任一条 F 用例未实现/实现与预期不符；单测假绿（断言不到位）或漏覆盖关键 F。

## 二、代码质量（Q）— quality 验收基准

| 维度 | 检查项 | 通过标准 |
|------|--------|---------|
| **命名** | 函数/变量/文件名 | 见名知意，无无意义缩写，符合语言惯例 |
| **函数设计** | 长度/参数/职责 | 函数 ≤ 50 行，参数 ≤ 4 个，一个函数做一件事（单一职责） |
| **重复代码** | 复制粘贴痕迹 | 相同逻辑已抽取；**高价值重复**（业务/逻辑重复：状态聚合/CRUD/校验/渲染）≥2 处 = FAIL；**低价值重复**（常量/图标/单行工具/字符串）只记建议 |
| **注释** | 解释性注释 | 复杂逻辑有注释，公共接口有文档串 |
| **设计模式** | 是否用了恰当模式 | 无明显反模式（God Class、长参数链等） |
| **一致性** | 与已有代码风格 | 命名风格/错误处理/导入顺序统一 |
| **视觉质量**（仅前端 UI 任务） | Anti-Slop 反模式 + 与 DESIGN.md 令牌对齐 | 无 P0（紫渐变/emoji 图标/圆角卡+彩条/编造数据/对比度不足/无响应式/资源 404）；P1 ≤ 2 条；偏离令牌注明差异 |
| **领域建模**（仅 `方法论：DDD` 模式） | 四层目录 + 依赖方向 + 贫血模型 + 聚合边界 + 仓储抽象 | 目录齐全、domain 零外部依赖、无贫血模型、聚合边界内聚、仓储只依赖接口 |

**FAIL**：命名问题 ≥ 3 处；或函数过长；或高价值重复 ≥ 2 处；或视觉 P0 任一条 / P1 ≥ 3 条（前端）；或 DDD 贫血模型/聚合破坏/依赖方向错。

## 三、健壮性（B）— robustness 验收基准

| 维度 | 检查项 | 通过标准 |
|------|--------|---------|
| **空值处理** | null/None/undefined | 所有外部输入都有空值检查 |
| **边界输入** | 空串/零值/负数/超长 | 边界输入不崩溃、行为可定义 |
| **异常处理** | try-catch 覆盖关键路径 | 文件读写/网络请求/数据解析有异常处理 + 降级行为 |
| **资源管理** | 文件句柄/连接/内存 | 异常路径也释放资源（with/try-finally/defer） |
| **输入验证** | 用户输入/API 参数 | 有明确的验证与拒绝逻辑 + 清晰错误信息 |

> 攻击面（注入/XSS/越权/密钥）归 security，本维度只管"代码会不会崩"。

**FAIL**：空值未检查、或有未捕获异常路径、或输入验证缺失。

## 四、安全性（S）— security 验收基准（攻击者视角）

| 维度 | 查什么 | 典型漏洞 |
|------|--------|----------|
| **注入** | 输入到解释器（SQL/shell/模板/LDAP）参数化；输出到 HTML 转义 | 拼接 SQL、`os.system(user_input)`、模板注入、XSS |
| **认证与会话** | 密码策略/会话管理/JWT 验证 | 弱密码、会话固定、JWT 不验签、登出未失效 |
| **访问控制** | 敏感操作权限校验；对象引用防枚举 | IDOR、垂直越权、缺失校验 |
| **敏感数据** | 密钥/token 硬编码；日志/错误泄露；密码存储 | 硬编码 `SECRET_KEY`、日志打印密码、明文存密码 |
| **配置** | CORS/默认凭据/调试模式/目录列表 | CORS `*`+凭据、admin/admin、生产开 debug |
| **依赖** | 已知 CVE | `npm audit` / `pip-audit` 高危 |
| **密码学** | 哈希/随机数/盐 | MD5/SHA1 存密码、`random` 生成 token、硬编码盐 |

**FAIL**：任一高危（注入/越权/硬编码密钥/明文密码/默认凭据/高危 CVE），或中危 ≥ 3。严重度：远程可利用无需认证=高危；需登录/特定条件=中危。

## 五、端到端（E）— e2e 验收基准

| 检查项 | 标准 |
|--------|------|
| 契约 E 场景逐条执行 | 按"用户流程"列实际执行命令/请求，比对实际输出与预期结果 |
| 时序图链路核查 | design.md 时序图调用链逐环断言；时序图有链路但契约漏列 → 补充执行 |
| 外部依赖独立环境 | Redis/MySQL/PG/Mongo 用测试容器；文件存储用跨平台临时目录 |
| 错误分支 | 时序图标注的错误分支构造失败场景，验证降级行为与错误信息 |

**FAIL**：任一场景执行失败或输出不符预期。

## 六、给 Dev 的执行要点（开发前对齐，省掉测试返工）

```
写代码前，用下面清单自查一遍"我会不会被测挂"：
- [ ] 函数 ≤ 50 行、参数 ≤ 4、单一职责（Q）
- [ ] 无复制粘贴的业务/逻辑重复（Q）
- [ ] 命名见名知意、风格与项目一致（Q）
- [ ] 所有外部输入：空值 + 边界 + 验证 + 异常处理 + 降级行为（B）
- [ ] 资源在异常路径也释放（B）
- [ ] 无注入风险（参数化/转义）、无硬编码密钥、敏感操作有权限校验（S）
- [ ] 前端 UI：对齐 DESIGN.md 令牌，无 Anti-Slop P0/P1（Q-视觉）
- [ ] 契约 F/B/S 用例都写了单测且断言到位（F）
```

> 这些维度同时是 **Tester 的判卷标准**——Dev 与 Tester 看同一张卷子，不是 Tester 临时出题。
