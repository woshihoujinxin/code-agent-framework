# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working in this repository.

## Overview

This is a **multi-agent autonomous development framework** (无人值守多智能体编码框架). It orchestrates software development through specialized agents that collaborate via file-based communication, implementing a three-layer loop: outer (continuous requirements), middle (batch development), and inner (bug fixes).

**Core architecture:** Requirements → Research（串行：调研→PM产品化） → Planner (with test contracts) → Frontend/Backend Devs (unit tests + self-check) → 5-Dimensional Testing (correctness/quality/robustness/security/E2E) → Fix Loop → code-sage rule extraction.

| `/goal-resume [继续]` | Resume from breakpoint | Scans `docs/main-log.md` CHECKPOINT + `docs/dev-plan.md` states, reports save point (empty arg) or resumes precisely per task state (`继续`) |
| `/goal-research <repo_urls>` | Research sub-pipeline (complex needs) | Clone repos → code-researcher → technical docs → auto-continue to `/goal-review` |
| `/goal-review <version>` | Design review gate (4-artifact gate + 4-party vote) | research/requirement/design-draft/prototype ready → gate → review meeting → resolution → `/goal-develop` |

> Use `/goal-develop` for development with 5-dimensional quality gates (functionality/quality/robustness/security/E2E). Use `/goal-deliver` for delivery with review→build→validation pipeline.

## Key Architecture Concepts

### Three-Layer Loop

1. **Outer layer** (continuous): Ingests requirements, never exits
2. **Middle layer ①** (development): Full-batch parallel dev → smoke check → mark 🔳 (pending test)
3. **Middle layer ②** (testing): Version-level 5-dimensional testing → fix loop (≤3 rounds)
4. **Inner layer** (self-evolution): code-sage extracts rules → coding-standards →下次迭代

### Test Contracts (F/B/S/E/Q)

The **test contract** in `docs/feature-spec.md` is the **shared baseline** for Dev unit tests and Tester verification — a hard contract that cannot be violated:

- **F (Functionality)**: Business use cases, Dev must cover with unit tests
- **B (Robustness)**: Boundary/edge cases, Dev must cover with unit tests
- **S (Security)**: Attack scenarios, Dev must cover with unit tests
- **E (E2E)**: End-to-end flows, verified by E2E tester
- **Q (Quality)**: Quality checklist (non-test format)

Each use case must include: US source, role (FE/BE/both), input, expected output. Dev self-check reports must declare "covered F/B/S case numbers". Tester reports must include "verification matrix by case".

### Worktree Testing

Tests run in a **version-level worktree** (`tests/ws-{version}`), not the main repository. This isolates testing from concurrent development. The worktree is checked out to the `feature/{version}` branch and synced before each test.

### DAG-Based Task Scheduling

Tasks are scheduled based on dependency graph (DAG) from `docs/dev-plan.md`:
- Tasks with satisfied dependencies form the **ready set** (`ready_dev`)
- All ready tasks are developed in parallel (default: maximize concurrency)
- After all ⏳ become 🔳, **Phase 3 testing begins** for the entire version

### Version Branching

All development and bug fixes commit to a **version branch** `feature/{version}` (version from `git tag`, e.g., v0.0.1). Testing is based on this branch (logical complete version). After all tests pass:
- Merge to main: `git checkout main && git merge feature/{version}`
- Tag: `git tag v{version}`
- Cleanup: Remove worktree and branch

### 调研流程（串行）

```
/goal-research
  ├─ Phase 1: 调研 → research.md + requirement.md
  ├─ Phase 2: PM 产品化（基于 requirement） → prd.md
  ├─ Phase 3: 原型（基于 prd） → prototype/
  ├─ Phase 4: 设计草案（基于 research + prd） → design-draft.md
  └─ 自动衔接 /goal-review

/goal-review
  ├─ gate: 检查评审材料齐备（research + requirement + prd + prototype + design-draft可选）
  ├─ 评审会议: 四方评审 → 投票 → 决议
  └─ 通过 → /goal-develop
```

**Task state emojis**: ⏳ pending | 🔄 in progress | 🔳 pending test | ✅ complete | ⚠️ low-quality pass

## Development Modes

| Mode | Trigger | Characteristics |
|------|---------|-----------------|
| **Standard SOP** | Multi-module/multi-end/complex state | Full process with 5-dimensional quality gates |
| **Quick Mode** | ≤10 source files/single-module/no complex state | Compressed loop (≤3 tasks, 1 test round, ≤2 fix rounds), **test contracts still produced**. **成果优先硬化**: correctness+e2e 通过后强制 checkpoint 暂停交付用户确认方向；修正 ≤2 轮(第2轮FAIL升级)；全程不触发 code-sage(交付前才精化) |
| **BugFix** | Explicit bug description | Resume relevant Dev + retest affected dimensions only, skip PM/Planner |
| **Stock Mode** (存量模式) | Existing project with source + git history | **Follow existing patterns** (architecture/testing/naming), don't force DDD/5-dim/full design docs; use project's own test commands for verification |

## DDD Methodology (Standard SOP + Complex Business Rules)

When injected `方法论：DDD` by the orchestrator (standard SOP + complex business rules), Planner extends to **domain modeling**:
- **Bounded contexts**: Divide business boundaries, write to design.md
- **Aggregates**: Identify aggregates/entities/value objects
- **Repository interfaces**: Per aggregate, signature-level definition
- **Directory skeleton**: `src/` with four-layer DDD structure (domain/application/interface/infrastructure)

Quick Mode/BugFix do NOT inject DDD.

## Important Constraints

- **UTF-8 hard constraint**: All logs/docs must be UTF-8. Never use shell `echo/printf >>` to append Chinese lines (will corrupt on Windows GBK). Use Write/Edit tools only.
- **Git commit mandatory**: Dev must commit to `feature/{version}` branch before testing. Tester reports must include commit hash.
- **IS_PASS mandatory**: Dev self-check reports must include `IS_PASS: YES/NO` line.
- **No direct code editing by orchestrator**: Orchestrator never edits code directly — all delegated to Dev agents.
- **Test contract immutability**: Contracts (F/B/S/E/Q) can only be changed by Planner, not Dev/Tester. If needed, route through Planner.
- **Concurrent control**: Two-layer concurrency — task-level (BATCH_SIZE) for development, dimension-level (MAX_PARALLEL, default 3) for testing. Peaks at max(2×|ready|, MAX_PARALLEL), never multiply.

## Three-Tool Compatibility

The same repository serves three tools with **single source of truth**:

| Capability | Claude Code | opencode | Reasonix |
|------------|-------------|----------|----------|
| 19 subagents | `agents/` (native) | `.opencode/agents/` (generated) | `.reasonix/skills/` (generated, runAs: subagent) |
| Commands | `commands/` (native) | `.opencode/commands/` (generated) | Native reads `.claude/commands`, zero changes |
| Knowledge base skills | `skills/` (native) | Native reads `.claude/skills`, zero changes | Native reads `.claude/skills`, zero changes |
| Project instructions | CLAUDE.md | AGENTS.md (fallback to CLAUDE.md) | REASONIX.md / AGENTS.md / CLAUDE.md |

opencode cannot use `/goal-init` for initialization (only reads `.opencode/commands/`, not `.claude/commands/`). Use terminal command: `python .claude/tools/sync-compat.py deploy .`
